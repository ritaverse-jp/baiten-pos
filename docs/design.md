## 0. 設計の前提（確定・変更不可）

| 層 | 採用技術 | 補足 |

| データストア | Google スプレッドシートのみ | 専用DB（Supabase / Firebase 等）は使わない |

## 1. スプレッドシートのタブ構成と列設計

要件定義 8 章を踏襲する。実装上の過不足として以下 3 点を追加し、1 点を運用方針で補う。

### 1.1 タブ構成

| タブ名 | 役割 | 更新方法 |
| --- | --- | --- |
| `商品マスタ` | 販売商品の一覧 | 商品管理画面から編集（GAS 経由） |
| `カテゴリ` | カテゴリの一覧 | カテゴリ管理画面から編集（GAS 経由） |
| `端末` | 利用端末の登録情報 | 端末の初回登録時に追記。状態列は管理者が操作 |
| `売上ログ_YYYYMM` | 月ごとの売上明細（1商品1行） | 会計確定時に GAS が追記（**追記専用**） |
| `操作ログ` | マスタ編集・会計取消の監査ログ | GAS が追記（**追記専用**）／**新設** |

売上ログは月ごとにタブを分ける（1タブの行数増大による動作低下の回避）。当月タブが存在しない場合は GAS が自動生成する。

### 1.2 `商品マスタ` タブ

| 列 | 項目 | 型 | 備考 |
| --- | --- | --- | --- |
| A | No. | 整数 | 一意。1〜99。画面上は①②③…の丸数字で表示 |
| B | 商品名 | 文字列 | 30文字以内 |
| C | 金額 | 整数 | 税込・0以上 |
| D | カテゴリ名 | 文字列 | `カテゴリ` タブのカテゴリ名と対応 |
| E | 表示順 | 整数 | 未指定時は No. 順 |
| F | 販売状態 | 文字列 | `有効` / `無効` |

### 1.3 `カテゴリ` タブ

| 列 | 項目 | 型 | 備考 |
| --- | --- | --- | --- |
| A | カテゴリ名 | 文字列 | 一意 |
| B | 表示順 | 整数 | 会計画面のタブ並び順 |
| C | 表示色 | 文字列 | 色コード等（任意） |

### 1.4 `端末` タブ（**修正案③：E列を追加**）

| 列 | 項目 | 型 | 備考 |
| --- | --- | --- | --- |
| A | 端末コード | 文字列 | **英大文字 1〜4 文字**（A・B・C…）。一意。数字・記号は不可（理由は 5.4） |
| B | 端末名 | 文字列 | 「レジ1」等の表示用名称 |
| C | 登録日時 | 日時 | 初回登録日時 |
| D | 状態 | 文字列 | `有効` / `無効`。**アクセス失効の唯一のスイッチ（7章）** |
| E | **最終同期日時** | 日時 | **GAS が売上受信のたびに更新** |

E 列の追加理由：管理者が「この端末は最近同期していない」＝未送信データが滞留している可能性をシート上で発見できるようにするため（NF-09 の運用補助）。

認証情報（トークンハッシュ等）は**この タブには置かない**。店舗スタッフがシートを閲覧できるため、Script Properties に保持する（7.2）。

### 1.5 `売上ログ_YYYYMM` タブ（**修正案①：K列を追加**）

| 列 | 項目 | 内容例 | 備考 |
| --- | --- | --- | --- |
| A | 日付 | 2026/07/23 | 会計確定日 |
| B | 時刻 | 14:32 | 集計・分析用 |
| C | 会計番号 | 20260723-A014 | 端末コードを含む一意の会計番号。同一会計の行を紐づけるキー |
| D | 端末コード | A | 会計を行った端末（端末別集計用） |
| E | 商品名 | からあげ串 | 確定時点の商品名 |
| F | 金額 | 450 | **割引適用後**の1点あたり単価 |
| G | 個数 | 2 | 取消時はマイナス値 |
| H | 小計 | 900 | 金額 × 個数 |
| I | 割引額 | 50 | 1点あたりの割引額 |
| J | 備考 | イベント割 | 会計単位の備考（同一会計の全行に同じ値） |
| K | **行番号** | 1 | **同一会計内の明細順。会計番号＋行番号で明細行が一意** |

K 列の追加理由：再送や取消の突き合わせで「この会計の何行目か」を特定するキーが必要。J 列までだと、同一会計内に同じ商品・同じ割引の行が 2 行ある場合（6.4 の「行を分ける」操作後）に区別できない。

### 1.6 `操作ログ` タブ（**修正案②：新設**）

| 列 | 項目 | 内容例 |
| --- | --- | --- |
| A | 日時 | 2026/07/26 14:32:05 |
| B | 端末コード | A |
| C | 操作種別 | `商品追加` / `商品編集` / `商品削除` / `カテゴリ追加` / `カテゴリ編集` / `カテゴリ削除` / `会計取消` / `端末登録` / `端末無効化` |
| D | 対象 | `商品No.3` / `会計番号 20260723-A014` |
| E | 内容 | `{"before":{"金額":500},"after":{"金額":550}}` 形式の JSON |

新設理由：NF-07（マスタ編集・削除、会計取消の操作ログ記録）と要件定義 5.4（マスタ編集操作のログ記録）が要求されているが、8 章のタブ構成に受け皿がなかった。

### 1.7 指摘：カテゴリ名を外部キーにするリスク（構成は変更しない）

`商品マスタ` D 列はカテゴリ名の文字列参照であるため、**カテゴリ名を変更すると商品側の参照が切れる**。

カテゴリ ID を導入する案もあるが、シートの人間可読性が下がる（管理者がシートを直接見て理解できることは本構成の利点）。したがって ID は導入せず、**GAS のカテゴリ改名処理が、同一ロック内で `商品マスタ` D 列の同名セルも一括置換する**ことで整合を保つ（2.6）。

## 2. GAS エンドポイント設計

### 2.1 共通仕様

- GAS Web アプリの入口は `doGet` / `doPost` の 2 関数のみ。**リクエストボディの `action` プロパティでルーティング**する
- **CORS 制約（重要）**：GAS はプリフライト（OPTIONS）に応答できない。POST は `Content-Type: text/plain` で JSON 文字列を送る「単純リクエスト」に限定し、GAS 側で `JSON.parse(e.postData.contents)` する。`application/json` を指定すると必ず失敗する
- 認証が必要な呼び出しは GET を使わず **POST に寄せる**。GET だとトークンがクエリ文字列に載り、GAS の実行ログに残る
- デプロイ設定：「自分として実行」「全員がアクセス可」。アクセス制御はアプリ層のトークン検証で行う（7 章）
- レスポンス形式を統一する

```json
{ "ok": true,  "data": { } }
{ "ok": false, "error": { "code": "TERMINAL_DISABLED", "message": "..." } }
```

- 主なエラーコード：`UNAUTHORIZED` / `TOKEN_EXPIRED` / `TERMINAL_DISABLED` / `LOCK_TIMEOUT` / `VALIDATION_ERROR` / `DUPLICATE_KEY` / `PIN_LOCKED`

### 2.2 エンドポイント一覧

| action | メソッド | 認証 | ロック | 概要 |
| --- | --- | --- | --- | --- |
| `ping` | GET | 不要 | なし | 疎通確認（設定画面の URL 検証用） |
| `registerTerminal` | POST | PIN | **あり** | 端末登録・端末コード発行・トークン発行 |
| `login` | POST | PIN | なし | 既存端末の再認証。トークン再発行 |
| `refreshToken` | POST | トークン | なし | 有効期限の巻き直し |
| `getMasters` | POST | トークン | なし | 商品・カテゴリ・自端末状態の一括取得 |
| `getTodayMaxSeq` | POST | トークン | なし | 自端末・当日の最大連番取得（採番カウンタ復元用） |
| `appendSales` | POST | トークン | **あり** | 売上明細の一括追記（冪等） |
| `saveProduct` | POST | トークン | **あり** | 商品の追加・編集 |
| `deleteProduct` | POST | トークン | **あり** | 商品の削除 |
| `saveCategory` | POST | トークン | **あり** | カテゴリの追加・編集（改名時はカスケード） |
| `deleteCategory` | POST | トークン | **あり** | カテゴリの削除（商品が紐づく場合は拒否） |
| `getSalesHistory` | POST | トークン | なし | 当日の全端末分の会計履歴（FR-14） |
| `cancelSale` | POST | トークン | **あり** | 会計取消（FR-15） |

### 2.3 `getMasters`

- 入力：`{ action, apiToken, terminalCode }`
- 出力：`{ products: [...], categories: [...], terminalStatus: "有効", fetchedAt }`
- 処理：`商品マスタ`・`カテゴリ` タブを全読みして JSON 化する。読み取り専用のためロック不要（追記中に読んでも、行単位で壊れた値が読めることはない）

### 2.4 `appendSales`（最重要）

**入力**

```json
{
  "action": "appendSales",
  "apiToken": "...",
  "terminalCode": "A",
  "sales": [
    {
      "saleId": "20260723-A014",
      "confirmedAt": "2026-07-23T14:32:00+09:00",
      "note": "イベント割",
      "lines": [
        { "lineNo": 1, "productName": "からあげ串",
          "netUnitPrice": 450, "qty": 2, "subtotal": 900, "discount": 50 }
      ]
    }
  ]
}
```

`netUnitPrice` は**割引適用後**の1点あたり単価（＝ シート F 列）。`discount` は 1 点あたりの割引額（＝ シート I 列）。

フィールド名を `unitPrice` ではなく `netUnitPrice` としているのは、伝票側（`TicketLine`）が持つ**割引前**の単価と取り違えないようにするため。両者は名前で区別する。

**出力**

```json
{ "ok": true, "data": { "results": [ { "saleId": "20260723-A014", "status": "appended" } ] } }
```

`status` は `appended`（新規追記）または `duplicate`（既に存在。追記せず成功扱い）。

**処理（すべてロック内で行う）**

1. `LockService.getScriptLock().waitLock(30000)`。取得できなければ `LOCK_TIMEOUT` を返す
2. `confirmedAt` から対象月タブ名 `売上ログ_YYYYMM` を決定。**存在しなければヘッダ行付きで自動生成**
3. 対象月タブの C 列を `TextFinder` で検索し、**既に存在する `saleId` の会計はスキップして `duplicate` を返す**（冪等性の担保）
4. 新規分の全明細行を二次元配列に組み立て、**1 回の `setValues` で末尾に一括追記**する。行ごとの `appendRow` 連打はしない（速度と、中途半端な行を残さないため）
5. `端末` タブ E 列（最終同期日時）を更新
6. `finally` で `releaseLock()`

### 2.5 `registerTerminal` / `getTodayMaxSeq`

**`registerTerminal`**

- 入力：`{ action, pin, terminalName: "レジ1", requestedCode: "A" }`（`requestedCode` は任意）
- 出力：`{ terminalCode, terminalName, apiToken, expiresAt }`
- 処理：ロック内で `端末` タブを読み、希望コードが空いていればそれを、未指定なら A→B→C… の空き最小を採番して追記。**端末コードの一意性はこのロックだけで保証される**。採番の根幹であるため、この処理のみ必ずオンラインかつ排他で行う。あわせてトークンを発行する（7 章）

**`getTodayMaxSeq`**

- 入力：`{ action, apiToken, terminalCode, date: "20260723" }`
- 出力：`{ maxSeq: 14 }`
- 処理：当月タブの C 列から `{date}-{terminalCode}` 前方一致の最大連番を返す。端末の IndexedDB が消えた際のカウンタ復元に使う（5.4）

### 2.6 マスタ更新系

`saveProduct` / `deleteProduct` / `saveCategory` / `deleteCategory` は共通して、ロック内で「対象行を特定 → 検証 → 上書き／削除 → `操作ログ` 追記」を行う。

- 同時編集は最後にロックを取った側が勝つ（要件定義 5.4 の「後勝ち」）
- `saveProduct`：No. 重複を拒否（`DUPLICATE_KEY`）。商品名 30 文字以内、金額 0 以上を検証
- `deleteProduct`：削除しても過去の売上ログには影響しない（売上ログは確定時点の商品名・金額を保持しているため）
- `saveCategory`：**カテゴリ改名時は同一ロック内で `商品マスタ` D 列の同名セルを一括置換する**（1.7 への対処）
- `deleteCategory`：商品が 1 件以上紐づく場合は拒否する（要件定義 6.3）

### 2.7 `cancelSale`（FR-15）

- 入力：`{ action, apiToken, terminalCode, saleId }`
- 処理：ロック内で元会計の全行を読み、**個数と小計をマイナスにした行を追記**する。元の行は削除しない。備考欄には `取消（元会計番号）` を自動記載し、`操作ログ` にも記録する。取消行の会計番号は新規採番せず元の `saleId` を保持する（グルーピングで相殺されるようにするため）

**未送信の会計は取り消せない【確定】**

GAS は元会計の行をシートから読んでマイナス行を作るため、まだシートに載っていない（未送信キューに残っている）会計は取り消せない。履歴画面では**未送信の会計の取消ボタンを非活性にし、同期完了後にのみ取消できる**ものとする（タスク18）。

キューから該当会計を取り下げる方式は採らない。「確定した会計は消さない・売上ログは追記専用」という原則（1.1・4.4）と衝突するため。

### 2.8 LockService の使い方

- **`getScriptLock()`（スクリプト全体で 1 本のグローバルロック）を全書き込み系で共有する。** 対象シートは 1 ファイルのみで `getDocumentLock()` と区別する意味がなく、種類を混在させると排他が効かない事故につながる
- パターンは常に固定する

```
ロック取得（waitLock 30秒）
  → 読み（重複チェック・行特定・空きコード探索）
  → 書き（setValues）
finally → releaseLock()
```

- **「チェックと書き込みを同一ロック内で行う」ことが本質。** 重複チェックをロック外に出すと check-then-act の競合が生じる
- タイムアウト時は `LOCK_TIMEOUT` を返すだけにし、リトライはクライアントの同期エンジンに任せる。GAS 側で待ち続けると 6 分の実行時間制限を圧迫する

## 3. フロントエンド構成

### 3.1 ディレクトリ構成

```
src/
├─ app/                 エントリ、ルーティング、プロバイダ、認証ガード
├─ screens/             画面（SC-xx と 1:1 対応）
│   ├─ checkout/        SC-01 会計画面・SC-02 精算モーダル
│   ├─ products/        SC-03 商品マスタ管理
│   ├─ categories/      SC-04 カテゴリ管理
│   ├─ history/         SC-05 会計履歴・取消
│   └─ settings/        SC-06 設定（端末登録・未送信一覧・手動同期）
├─ domain/              純粋ロジック層（React にも通信にも依存しない）
│   ├─ types.ts         商品・カテゴリ・伝票・売上・端末の型定義
│   ├─ calc.ts          行小計・合計・釣銭（要件定義 6.7）
│   ├─ saleNumber.ts    会計番号の生成・パース
│   └─ ticket.ts        伝票操作（行追加・+1・行を分ける・割引検証）
├─ state/               Zustand ストア
│   ├─ ticketStore.ts   入力中伝票（変更のたび IndexedDB へ永続化）
│   ├─ masterStore.ts   商品・カテゴリキャッシュ
│   └─ syncStore.ts     接続状態・未送信件数（画面上部バッジ用）
└─ data/
    ├─ gas/             GAS 通信層（text/plain POST・タイムアウト・エラー正規化）
    ├─ db/              IndexedDB 層（Dexie スキーマとアクセサ）
    └─ sync/            同期エンジン（キュー消化・接続監視・採番カウンタ）
gas/                    Apps Script 側（clasp 管理）
```

### 3.2 層の分け方の方針

- **`domain/` は純粋関数のみとする。** React・通信・Dexie のいずれにも依存させない。金額計算（6.7）と採番（5.4）はここで完結させ、UI バグ・通信バグと切り離す。テストはこの層に集中させる
- 状態管理は Zustand。`ticketStore` は書き込みのたびに Dexie へ保存し、起動時に復元する（NF-04）
- Service Worker（Workbox）は**アプリ本体（HTML/CSS/JS）の precache のみ**を担当し、**GAS への API 通信はキャッシュ対象にしない**。データの鮮度とキュー制御はアプリ層（`data/sync`）の責務に一本化する。ここを二重管理にすると、古いマスタが表示される・送信済み判定がずれる等の追跡困難な不具合を生む

### 3.3 Dexie テーブル構成（要件定義 8.3 の具体化）

| テーブル | 主キー | 内容 |
| --- | --- | --- |
| `products` | No. | 商品マスタキャッシュ |
| `categories` | カテゴリ名 | カテゴリキャッシュ |
| `currentTicket` | 固定キー 1 件 | 入力中伝票（NF-04） |
| `sales` | saleId | 当日確定済み会計（履歴表示用。`synced` フラグ付き） |
| `pendingQueue` | saleId | 未送信キュー（送信ペイロード・`retryCount`・`lastError`） |
| `counters` | `YYYYMMDD` | 当日連番カウンタ |
| `config` | 固定キー | 端末コード・端末名・apiToken・有効期限・GAS URL |

## 4. オフライン設計

要件定義 9.1 により、オフライン動作は**必須要件**。

### 4.1 会計確定から同期までのフロー

```
[会計確定タップ]
  1. 採番：counters を Dexie トランザクション内で read → +1 → write
  2. 同一トランザクション内で
       sales へ保存 ＋ pendingQueue へ投入 ＋ currentTicket をクリア
  3. UI は即座に次の会計へ（ここまで完全ローカル → NF-02 を構造的に満たす）
  4. 同期エンジンを非同期に起動（fire-and-forget）

[同期エンジン]（シングルトン・多重起動ガード付き）
  起動契機：アプリ起動時 / online イベント / visibilitychange /
            会計確定時 / 30秒間隔（未送信 > 0 の間のみ）/ 設定画面の手動実行
  処理：pendingQueue を古い順に最大 N 件まとめ、appendSales へ 1 リクエストで送信
        → 応答の saleId ごとに appended / duplicate を確認
             → sales.synced = true にして pendingQueue から削除
        → 失敗（通信断・LOCK_TIMEOUT 等）
             → retryCount++、指数バックオフで次回へ。キューには残す
```

- 未送信件数と接続状態は画面上部に常時表示する（要件定義 9.1）
- 未送信 1,000 件超過で管理者に警告を表示する（要件定義 9.1）
- ステップ 3 の時点で会計は成立している。**会計成立はネットワークに一切依存しない**

### 4.2 二重送信を防ぐ仕組み

ネットワークでは「送信は届いたが応答が返らなかった」状態を原理的に排除できない。したがって、

**クライアントは at-least-once（受理応答を得るまで再送）／サーバーは冪等（同じものは 2 回書かない）** の組み合わせで exactly-once 相当の効果を得る。

| 側 | 保証 |
| --- | --- |
| クライアント | 受理応答を受け取るまで `saleId` をキューから削除しない。応答の取りこぼしは必ず再送で回収される |
| GAS | `appendSales` が**ロック内で** C 列の `saleId` 存在チェックを行い、存在すれば追記せず `duplicate` を返す |
| クライアント | `duplicate` を成功と同義に扱い、キューから削除する |

**破綻しない根拠**：チェックと追記が同一ロック内のクリティカルセクションにあるため、同じ `saleId` を持つリクエストが 2 本同時に到達しても（例：自動同期と手動同期の競走）、後の 1 本は必ず先の追記結果を読んでスキップする。`saleId`（会計番号）は 5 章の方式で全端末を通して一意であるため、重複チェックのキーとして安全に使える。

### 4.3 通信復帰の検知

`navigator.onLine` および `online` イベントは、「Wi-Fi には接続しているがインターネットに出られない」状態を誤ってオンラインと判定する。したがって、

- **トリガーとしてのみ使い、状態の真実としては使わない**
- 接続状態インジケータの真実は**直近の GAS リクエストの成否**とする（成功 → オンライン表示、失敗 → オフライン表示）
- `online` イベント・定期タイマー・`visibilitychange` は「同期を試すきっかけ」に過ぎず、実際に送信できたかどうかで状態を更新する

### 4.4 未送信キューの保全

- **認証エラーでキューを削除してはならない**（7.5 に詳細）。キューの消失は売上の消失を意味する
- 未送信データがある状態でのログアウトは警告を表示する（要件定義 9.1）
- IndexedDB キャッシュのうち、`pendingQueue` 以外はいつ破棄されても正データから復元できる。`pendingQueue` のみ消失させてはならない（要件定義 8.4）

## 5. 会計番号の採番（複数台対応）

**形式：`YYYYMMDD-{端末コード}{連番3桁}`（例 `20260723-A014`）**

### 5.1 実装方針

1. **端末コードの一意性はサーバーが保証する。** 初回セットアップ時（必ずオンライン）に `registerTerminal` がロック内で空きコードを採番し、端末に固定保存する。**ここが唯一の中央調整ポイントであり、運用開始後は中央調整が一切不要になる**
2. **連番は端末ローカルで採番する。** Dexie の `counters` テーブル（キー＝当日日付 `YYYYMMDD`）を、会計確定処理と**同一トランザクション内**で read → +1 → write する。日付が変われば別キーとなり、自然に 001 から再開する

### 5.2 一意性の根拠

| 観点 | 根拠 |
| --- | --- |
| 端末間 | 端末コードが異なるため名前空間が分離されている。**全端末が同時にオフラインでも衝突しえない** |
| 端末内 | カウンタの増加と会計データの保存が同一 Dexie トランザクションであるため、二重タップや処理の同時実行でも同一番号が 2 会計に付くことはない |

### 5.3 既知のリスクと対処

| リスク | 対処 |
| --- | --- |
| IndexedDB が消去され、カウンタが 001 に戻る（ブラウザのデータ削除等） | 起動時に「端末コードは設定済みだがカウンタが未初期化」を検知したら、オンラインで `getTodayMaxSeq` を呼び、**シート上の当日最大連番 + 1 から再開**する。オフラインで復元できない場合は会計開始をブロックし、その旨を表示する（「端末データを消した直後に圏外で営業開始」という極端なケースのみ該当） |
| 万一の番号衝突 | GAS の重複チェックが**内容の異なる同一 saleId** を検出した場合はエラーを返す。静かな上書きや混入は起きない（最後の防波堤） |
| 端末時計のずれによる日付誤り | 設定画面に、端末時刻とサーバー時刻のずれを検知して警告表示する（運用上の注意喚起） |
| 1 日 1 端末 999 件超 | 売店規模では想定外。超過時は連番を 4 桁に自然延長する（5.4 により延長してもパースは壊れない） |

### 5.4 端末コードを英大文字に限定する理由

会計番号は「ハイフン以降の**末尾の数字列が連番**、その手前が端末コード」という構造で解釈する。

端末コードに数字を許すと、連番が 999 を超えて 4 桁に延びた時点で `20260723-A1014` が `A1` + `014` なのか `A10` + `14` なのか判別できなくなる。端末コードを英字に限定すれば、連番が何桁になっても「末尾の数字列＝連番」で一意に切り出せる。

人間向けの表示名は `端末` タブ B 列の端末名（「レジ1」等）が担うため、コードを英字に絞っても運用上の不都合はない。

## 6. 認証とトークン失効（NF-05 / NF-09）

### 6.1 前提となる修正

PIN のみを検証して払い出すトークンは全端末で同じ値になり得るため、**端末単位での無効化が原理的に不可能**である。したがってトークンは端末に 1 対 1 で紐づける。

### 6.2 トークンの発行と保持

- 初回セットアップ（必ずオンライン）で `registerTerminal` が**端末コードとトークンを同時に発行**する
- 以後の再認証（`login`）も端末コードとセットでしか行えない
- トークン実体は不透明なランダム文字列。GAS 側は **SHA-256 ハッシュのみを Script Properties に保持**する（キー `token_<端末コード>` → `{ hash, expiresAt, epoch }`）
- **スプレッドシート上には認証情報を置かない。** 店舗スタッフがシートを閲覧できるため、シートに載せると失効の意味が薄れる
- PIN も同様にハッシュのみを Script Properties に保持する

### 6.3 失効スイッチ

認証が必要な全リクエストで以下を検証する。

```
トークン → ハッシュ照合 → 端末コード特定
        → 端末タブ D 列「状態」が「有効」か
        → 有効期限内か
        → トークンエポックが現行値と一致するか
```

このうち**人間が操作するのは `端末` タブ D 列だけ**とする。管理者はシート上でセルを `無効` に変更するか、スプレッドシートのカスタムメニュー「この端末を無効化」を実行する。GAS はステートレスでリクエストごとに検証するため、セッションが生き残ることはない。

**無効化はフラグ判定で終わらせず、破壊的に行う。** 状態が `無効` になった時点で、GAS はその端末の Script Property（トークンハッシュ）自体を削除する。

理由：紛失端末を拾得した者が PIN を知っていた場合、フラグを戻した瞬間に古いトークンが復活してしまう。実体を削除しておけば、再有効化しても PIN による再ログインを経ないとアクセスできない。`login` 側でも状態を検証するため、無効な端末は再ログインもできない。

### 6.4 失効の即時性

リクエストのたびに `端末` タブを読むと数百ミリ秒の遅延が乗るため、端末状態は `CacheService` に 60 秒キャッシュする。失効が最大 60 秒遅れることを避けるため、以下 2 経路でキャッシュを即時破棄する。

| 経路 | 挙動 |
| --- | --- |
| カスタムメニューから無効化 | 同一処理内でキャッシュを削除（遅延ゼロ） |
| シートを手編集 | `onEdit` トリガーが `端末` タブの編集を検知してキャッシュを削除 |

トリガーが動作しない場合でも最大 60 秒で失効するため、紛失対応としては十分と判断する。

### 6.5 有効期限

- **絶対期限 90 日**とする。スライディング期限（使用のたびに延長）は、リクエストごとに Script Property への書き込みが発生し書き込み回数の割当を圧迫するため採用しない
- 残り 14 日を切ったら、フロントがオンライン時に `refreshToken` を静かに呼んで巻き直す（現行の有効なトークンで認証するため PIN 入力は不要）
- 期限切れまで放置された場合のみ PIN 再ログインを求める

**一斉失効**：どの端末が紛失したか特定できない場合に備え、Script Properties に `tokenEpoch` を持つ。管理者がメニューから「全端末を失効」を選ぶとエポックが 1 つ進み、それ以前に発行された全トークンが一括で無効になる。PIN 変更時も同時にエポックを進める。

### 6.6 オフライン層との噛み合わせ

**認証エラーで未送信キューを削除してはならない。** 削除は売上の消失を意味する。エラーコードで挙動を分ける。

| エラー | 同期エンジン | 画面 |
| --- | --- | --- |
| `TOKEN_EXPIRED` | 同期を一時停止。**キューは保持** | PIN 再ログインを促す。成功後に自動で同期再開 |
| `TERMINAL_DISABLED` | 同期を恒久停止。**キューは保持** | 「この端末は管理者により無効化されています」＋未送信件数を表示 |

`TERMINAL_DISABLED` の端末には、**未送信データを CSV でエクスポートする経路を残す**。無効化は盗難端末を止めるための機能だが、誤操作や端末故障による無効化もあり得るため、正当な売上を手動で回収できる出口が必要となる。

### 6.7 PIN の総当たり対策

`login` は PIN のみが鍵となるため、`CacheService` に端末コード別の失敗回数を保持し、**5 回失敗で 15 分ロック**する（`PIN_LOCKED`）。GAS からクライアント IP を確実に取得することはできないため、端末コード単位での制限とする。

## 8. 難所の設計根拠まとめ

| 難所 | 採用方式 | 破綻しない根拠 |
| --- | --- | --- |
| オフラインキュー | ローカル確定 ＋ at-least-once 再送 | キュー削除は「サーバー受理応答の受領後」のみ。応答喪失は再送で回収され、重複はサーバーの冪等性が吸収する。会計成立がネットワークに一切依存しない |
| 複数台の採番 | 端末コード（サーバー採番）× ローカル連番 | 名前空間が端末ごとに分離され、運用中の中央調整がゼロ。端末内は Dexie トランザクションで直列化。カウンタ消失時のみ `getTodayMaxSeq` で復元 |
| 同時追記の競合 | ScriptLock 1 本 ＋ ロック内 check-then-append | 全書き込みが単一のグローバルロックで直列化され、重複チェックと追記が同一クリティカルセクションにある。追記は 1 回の `setValues` のため中途半端な行が残らない |
| 端末紛失時の失効 | 端末別トークン ＋ 状態列を唯一のスイッチ ＋ 破壊的失効 | 検証がリクエストごとのステートレス処理のためセッションが生き残らない。トークン実体を削除するため再有効化でも復活しない。キャッシュは無効化操作と `onEdit` で即時破棄 |
